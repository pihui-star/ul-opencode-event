# DNS 回退“长等待”优化计划

## 现状判断
- 是的，你的理解基本正确：当前逻辑是先走 nodemailer 默认解析/连接，失败后再进入 `dns.lookup` 回退。
- 当默认路径命中 DNS 超时时，会先消耗一段等待时间，所以整体看起来“修好了但慢”。

## 优化目标
1. 减少首轮等待时间，避免每次都等超时才回退。
2. 保留兼容性：在正常网络下不影响原有成功路径。
3. 让行为可控：允许按配置开启“快速回退模式”。

## 执行方案

### 方案 A（推荐）：预解析优先 + 失败再原始域名兜底
- 在测试连接/发送前先执行一次快速 `dns.lookup`（可设置短超时策略）。
- 若解析成功，优先使用 IP + `tls.servername=原域名` 直接连 SMTP。
- 若预解析失败，再回退到原始 host（保持兼容）。
- 预期效果：绕过 nodemailer 内部慢 DNS 路径，显著降低超时等待。

### 方案 B：新增可配置开关（默认兼容）
- 在 SMTP 配置中新增可选字段（例如 `dnsStrategy`）：
  - `auto`（默认）：维持现状；
  - `preferLookup`：优先走预解析；
  - `lookupOnly`：仅走预解析结果；
- 用户可按网络环境自助切换，无需改代码。

### 方案 C：超时参数收敛
- 为 nodemailer transporter 增加合理超时配置（连接、问候、socket）。
- 将“等待上限”显式收紧，避免单次卡顿过长。

### 方案 D：结果缓存（可选增强）
- 对成功解析的 host 做短 TTL 内存缓存（例如 5~10 分钟）。
- 连续多次 `test` 或高频通知时，减少重复解析成本。

## 验证计划
1. 基线：记录当前 `node dist/cli.js test` 总耗时。
2. 应用方案 A/B/C 后重复测试至少 3 次，比较平均耗时与最慢耗时。
3. 验证成功率：确保仍能发出测试邮件，且失败提示清晰。
4. 回归：确认普通网络环境下不引入新失败。
